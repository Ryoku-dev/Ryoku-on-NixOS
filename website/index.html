05 // INSTALL

Three steps in.
No Nix wizardry required.

Fresh NixOS is enough. Ryoku installs on top of your existing system and leaves your bootloader, disks, kernel and graphics configuration under your control.

01Enable flakes

Add this inside /etc/nixos/configuration.nix.

nix.settings.experimental-features = [
  "nix-command"
  "flakes"
];
sudo nixos-rebuild switch
02Make NixOS flake-based

Create /etc/nixos/flake.nix, then rebuild from it.

sudo nixos-rebuild switch --flake /etc/nixos#nixos
Open the beginner flake example →
03Install Ryoku

Preview the installer first if you want to see exactly what changes.

nix run github:aethctl/Ryoku-on-NixOS/main#install -- --dry-run

Then install:

nix run github:aethctl/Ryoku-on-NixOS/main#install

06 // FAQ

Common questions.
Short answers.

01How do I enable flakes?+

Add this to /etc/nixos/configuration.nix:

nix.settings.experimental-features = [
  "nix-command"
  "flakes"
];

Then run sudo nixos-rebuild switch.

02What should a beginner flake.nix look like?+ 
{
  description = "My NixOS system";

  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-26.05";

  outputs = { nixpkgs, ... }: {
    nixosConfigurations.nixos = nixpkgs.lib.nixosSystem {
      system = "x86_64-linux";
      modules = [ ./configuration.nix ];
    };
  };
}

Rebuild with sudo nixos-rebuild switch --flake /etc/nixos#nixos.

03How do I update Ryoku?+ 
ryoku update

That's it. Ryoku advances its configured flake input, builds a new NixOS generation and switches to it.

04Does Ryoku replace NixOS?+

No. Ryoku integrates into your existing NixOS configuration. Your bootloader, kernel, disks and hardware-specific graphics setup remain owned by your host configuration.

05What if an update breaks?+

Ryoku updates create normal NixOS generations, so previous generations remain available through standard NixOS rollback and boot-menu mechanisms.

力 // PORT ARCHITECTURE

HOW DOES IT WORK?

Ryoku on NixOS is not a rewrite and it is not a pile of copied dotfiles. The port keeps upstream Ryoku intact where possible, then translates the assumptions an Arch system normally provides into Nix-native equivalents.

01UPSTREAM RYOKU

Arch-oriented shell, helpers, QML, scripts and desktop behavior remain the source of truth.

→
02PACKAGE LAYER

Nix derivations package the shell, plugins and helpers into reproducible, immutable store paths.

→
03RUNTIME BRIDGE

Wrappers, declared PATHs and user services expose the commands and runtime dependencies upstream expects.

→
04STATE BRIDGE

Package-owned code stays immutable while genuinely writable settings, caches and generated state live in user-owned paths.

→
05NIXOS MODULE

The desktop is attached declaratively to your existing NixOS system without taking ownership of your hardware config.

TRANSLATION, NOT EMULATION

Arch assumptions become Nix declarations.

Where upstream expects a binary on PATH, a mutable file, a service, or a desktop helper, the port supplies the NixOS equivalent instead of pretending the machine is Arch.

ONE QT STACK

QML stays ABI-consistent.

Quickshell, Qt and private multimedia pieces are built from the same Nix package set so the shell does not mix incompatible Qt internals.

HOST OWNERSHIP

Your NixOS system stays yours.

Ryoku does not seize your kernel, bootloader, disks or GPU configuration. Those remain in your host configuration; Ryoku adds the desktop layer.

GENERATIONS

Updates are normal NixOS rebuilds.

ryoku update advances the Ryoku flake input, builds a new generation and switches to it. Previous generations remain available for rollback.

THE RESULT Upstream Ryoku behavior on a reproducible NixOS foundation.
